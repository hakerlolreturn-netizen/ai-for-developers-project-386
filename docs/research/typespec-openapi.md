# Исследование: TypeSpec и сгенерированный OpenAPI

Тикет: #6 «Как подключить TypeSpec и использовать сгенерированный OpenAPI» (карта #5). Дата: 2026-10-28.

TypeSpec принят как источник контракта (ADR 0004, ещё не закоммичен). Здесь варианты подключения и их компромиссы, а не готовая настройка.

## Как проверялось

- Версии и peer-зависимости: `npm view` на 2026-10-28.
- Опции эмиттера: README установленного `@typespec/openapi3`.
- Генерация, дрейф, интеграция с Fastify и `openapi-typescript`: пробный проект вне репозитория (`/tmp`, Node v26, Fastify из npm latest, один маленький `main.tsp` с `GET`/`POST /api/event-types`). Что запускалось и что получилось, указано в тексте; в репозитории ничего не ставилось.
- Страницы typespec.io отдаются слишком большими (навигация съедает лимит чтения), поэтому опции эмиттера взяты из README пакета, а не со страницы сайта.

| Пакет                | Версия | engines.node |
| -------------------- | ------ | ------------ |
| `@typespec/compiler` | 1.17.0 | `>=22.0.0`   |
| `@typespec/http`     | 1.17.0 | `>=22.0.0`   |
| `@typespec/openapi3` | 1.17.0 | `>=22.0.0`   |
| `openapi-typescript` | 7.13.0 | не указан    |
| `openapi-fetch`      | 0.17.0 | не указан    |
| `@fastify/swagger`   | 9.9.2  | не указан    |

- `@typespec/openapi3@1.17.0` требует peer `@typespec/compiler ^1.17.0`, `@typespec/http ^1.17.0` и `@typespec/openapi ^1.17.0` (плюс ряд пакетов `0.87.x`, `@typespec/json-schema`). Компилятор, `http` и `openapi3` надо обновлять вместе.
- Node в репозитории 24 (`.nvmrc`), требование `>=22` выполняется.

Вывод: пиновать три пакета одной минорной линией (`^1.17.0`, как остальные зависимости репозитория); точность версий обеспечивает `package-lock.json`.

## 1. Где живёт TypeSpec

### Вариант A. Отдельный workspace `api/` (рекомендуется)

Каталог `api/` с `package.json`, `main.tsp`, `tspconfig.yaml`; в корневой `package.json` добавить в `workspaces`.

- Плюс: контракт принадлежит и бекенду, и фронтенду, ни один из них не владеет им; зависимости компилятора не попадают в `backend`/`frontend`.
- Плюс: сгенерированные артефакты лежат в одном месте, оба потребителя импортируют их из пакета `api`.
- Минус: ещё один workspace. Корневые скрипты `typecheck` и `build` вызывают `npm run <script> --workspaces` (для `typecheck` без `--if-present`), поэтому в `api/package.json` обязательны оба скрипта `typecheck` и `build`; `test` необязателен (`--if-present`).
- Порядок запуска workspaces в `npm run --workspaces` не проверялся; чтобы не зависеть от него, генерацию лучше вызывать явным корневым скриптом (см. раздел 5).

### Вариант B. Каталог внутри `backend/`

- Плюс: нет нового workspace, зависимости компилятора в `backend/package.json`.
- Минус: фронтенд тянет артефакты из чужого workspace через относительный путь; контракт выглядит частью бекенда, хотя ADR 0004 делает его общим.

### Вариант C. Корневой каталог без `package.json`

- Плюс: минимум файлов.
- Минус: зависимости компилятора приходится класть в корневой `package.json`, где сейчас только dev-инструменты; нет собственных скриптов `build`/`typecheck`.

## 2. Как эмитится OpenAPI

Минимальная конфигурация, которая проверена в пробном проекте (`npx tsp compile .` отработал успешно):

```yaml
# tspconfig.yaml
emit:
  - '@typespec/openapi3'
options:
  '@typespec/openapi3':
    openapi-versions: ['3.1.0']
    output-file: openapi.yaml
```

Источник опций: README `@typespec/openapi3@1.17.0`.

- `openapi-versions`: допустимы `3.0.0`, `3.1.0`, `3.2.0`; по умолчанию `["3.0.0"]`.
- `file-type`: `yaml` по умолчанию, если не выводится из расширения `output-file`; допустим массив для нескольких форматов.
- `output-file`: по умолчанию `{service-name-if-multiple}.{version}.openapi.yaml`; для одного сервиса без версий пример в README даёт `openapi.yaml`.
- `omit-unreachable-types`: по умолчанию в документ попадают все типы из пространства имён сервиса; с флагом только достижимые из операций.
- `seal-object-schemas`: по умолчанию `false`; при `true` модели получают `additionalProperties: false`.
- `new-line`: `lf` по умолчанию.
- Выходной каталог по умолчанию: `tsp-output/@typespec/openapi3/` (проверено: файл `tsp-output/@typespec/openapi3/openapi.yaml`). Меняется флагом `--output-dir` (есть в `tsp compile --help`) или `output-dir` в конфиге.
- Повторная генерация даёт побайтово тот же файл (проверено `cmp` на двух запусках), то есть вывод детерминирован и подходит для сравнения в CI.
- `tsp compile --warn-as-error` превращает предупреждения в ошибку (флаг есть в `--help`).

Выбор версии OpenAPI:

- `3.0.0` (по умолчанию): схемы в диалекте OpenAPI 3.0 (в нём nullable выражается ключевым словом `nullable`); Fastify в документации как раз показывает `nullable: true`.
- `3.1.0`: проверено, что сгенерированные схемы принимаются валидатором Fastify (Ajv) и корректно обрабатывают запрос и ответ (см. раздел 3). По спецификации OpenAPI 3.1 схемы совместимы с JSON Schema; для этого проекта разницы пока нет, нулевых значений в модели нет. Рекомендация: `3.1.0`, пересмотреть, если эмиттер или потребитель начнёт мешать.

## 3. Как Fastify использует результат

Факты из документации Fastify (Validation-and-Serialization):

- Схемы маршрутов Fastify это JSON Schema, валидация через Ajv v8, по умолчанию `coerceTypes: 'array'`, `useDefaults: true`, `removeAdditional: true`, `allErrors: false`.
- Схемы ответов сериализуются через fast-json-stringify, ключ схемы это код ответа (`'2xx'`, `default` тоже допустимы).
- Общие схемы регистрируются `addSchema()` и подключаются через `$ref` по `$id`.

Проверено в пробном проекте: сгенерированный `openapi.yaml` (3.1.0) читается `yaml`, схемы из `components.schemas` регистрируются через `addSchema`, схемы `requestBody` и `responses` подставляются в `schema.body` и `schema.response`. Результат: корректное тело даёт 201, тело без `durationMinutes` даёт 400 `FST_ERR_VALIDATION` (`body must have required property 'durationMinutes'`). `format: int32` Ajv Fastify принял без ошибки.

Нюанс, который пришлось обойти: `$ref` вида `#/components/schemas/EventType` Fastify не нашёл («Cannot find reference»). Помогла замена префикса `#/components/schemas/` на `urn:s:` во всём документе и регистрация схем с `$id: urn:s:<Имя>`. То есть нужен небольшой слой загрузки (ссылки плюс чтение YAML), готовой функции в Fastify нет.

Варианты:

### Вариант 1. Собственный загрузчик OpenAPI в `backend` (рекомендуется)

Небольшая функция читает `openapi.yaml`, переписывает `$ref`, регистрирует схемы и отдаёт схему операции по `operationId`.

- Плюс: валидация запросов и ответов идёт по тому же контракту, что и типы; мало зависимостей (парсер YAML).
- Плюс: поведение понятно и тестируется (как в пробе).
- Минус: загрузчик поддерживаем мы сами; схемы маршрутов подключаются явно, каждую операцию нужно связать с обработчиком вручную.
- Минус: TypeScript-типы тела и параметров приходится указывать явно, например `app.post<{ Body: components['schemas']['NewEventType'] }>`; автоматического вывода из подключённой во время выполнения схемы нет.

### Вариант 2. Готовый плагин, читающий OpenAPI (например `fastify-openapi-glue`)

- Существует (версия 4.12.0, `engines.node >=20`); его README и поведение в рамках исследования не читались и не проверялись.
- Предположительно снимает ручную привязку маршрутов, ценой зависимости от сторонней библиотеки и её совместимости с Fastify 5. Требует отдельной проверки до выбора.

### Вариант 3. Type provider (`@fastify/type-provider-json-schema-to-ts` и др.)

- Документация Fastify перечисляет официальные провайдеры для `json-schema-to-ts`, `typebox`, `zod` и требует схем, известных на этапе компиляции (для переменной нужен `as const`).
- Схема из `openapi.yaml` читается во время выполнения, поэтому вывод типов из неё не сработает (вывод автора по описанию документации, в пробе не проверялся). Подходит только если схемы генерировать в TS-код, а это отдельная генерация, не описанная в документации TypeSpec, прочитанной здесь.
- Для этого проекта не рекомендуется.

### Вариант 4. Документация и без валидации по контракту

`@fastify/swagger` в статическом режиме (`mode: 'static'`, `specification.path`) отдаёт готовый файл как документацию; в динамическом режиме строит документ из схем маршрутов. Для валидации не нужен и сам по себе контракт с бекендом не связывает. Опционально, если захочется Swagger UI.

Типы для бекенда: `openapi-typescript` из того же `openapi.yaml` даёт `components['schemas'][...]` и `paths`/`operations` (проверено, вывод есть). Использовать их в обработчиках и в тестах.

## 4. Как фронтенд получает типы и клиент

### Вариант I. `openapi-typescript` + `openapi-fetch` (рекомендуется)

- Генерация типов: `openapi-typescript <openapi.yaml> -o <file>.d.ts` (команда из документации `openapi-ts.dev`; в пробе вывод получен).
- Клиент: `createClient<paths>({ baseUrl })`, вызовы `GET`/`POST` с типизированными путём, параметрами и телом, результат `data`/`error`/`response` (документация `openapi-fetch`). Документация указывает размер около 6 kB и рекомендует `noUncheckedIndexedAccess`.
- Плюс: тот же набор типов можно использовать в бекенде; нулевой рантайм-генерации, клиент тонкий.
- Минус (проверено): у `openapi-typescript@7.13.0` `peerDependencies.typescript` равен `^5.x`, а в репозитории `typescript ~7.0.2`. В пробе `npm i openapi-typescript typescript@7` завершился `ERESOLVE`. Значит `npm ci` в репозитории упадёт без обхода (`overrides` для peer, `legacy-peer-deps` в `.npmrc` или отдельный `typescript@5` внутри `api/`). Генератор запустился через `npx` и вывел корректные типы, то есть это проблема разрешения зависимостей, а работоспособность на TS 7 как peer отдельно не проверялась. Это главный риск варианта; решение нужно принять до реализации (тикет #11).
- Минус: типы это `.d.ts` с форматированием генератора (4 пробела, точки с запятой), что не проходит `prettier --check .` с текущим `.prettierrc` (`semi: false`, `singleQuote: true`), если файл закоммичен и не исключён (см. раздел 5).

### Вариант II. Только типы, `fetch` вручную

Использовать `openapi-typescript` как есть, а запросы писать вручную с типами из `components`.

- Плюс: меньше зависимостей во фронтенде (нет `openapi-fetch`).
- Минус: путь, метод и тело не связываются с контрактом автоматически; ошибки в URL видны только в рантайме.

### Вариант III. Другие генераторы клиентов (orval, hey-api и подобные)

Не исследовались. Дают готовые функции или хуки, но больше сгенерированного кода и ещё одна зависимость, у каждой своя совместимость с TS 7.

### Вариант IV. Типы пишутся вручную

Не рекомендуется: теряется смысл ADR 0004.

## 5. Дрейф TypeSpec и OpenAPI в CI

Текущий `ci.yml` выполняет `npm ci`, `lint`, `typecheck`, `test`, `build` на каждый push и pull request. `lint` это `oxlint --deny-warnings && prettier --check .` по всему репозиторию.

### Вариант X. Не коммитить сгенерированное, генерировать перед каждой командой (рекомендуется)

`openapi.yaml` и `.d.ts` в `.gitignore`; корневой скрипт `gen` (`npm run build -w api` или аналог) вызывается из `pretypecheck`, `pretest`, `prebuild`, `predev` (хуки `pre*` npm; для корневых скриптов `typecheck`/`test`/`build`/`dev`). В CI дополнительных шагов не нужно: дрейфа быть не может, потому что файла в git нет; расхождение кода с контрактом ловит `typecheck` и тесты.

- Плюс: нет шума в диффах и конфликтов слияния, нет шага «забыл перегенерировать», `prettier` и `oxlint` не видят сгенерированных файлов (при игнорировании каталога).
- Минус: после `git clone` и `npm ci` ничего не работает до генерации; IDE без запуска `gen` показывает ошибки импорта; контракт в ревью виден только по `.tsp`, итоговый OpenAPI по диффу не видно.
- Минус: если тесты или `typecheck` запускают напрямую в workspace (`npm test -w backend -- ...`, как в `AGENTS.md`), хуки корневого скрипта не сработают. Нужно либо хуки в `package.json` самих workspaces, либо дописать в `AGENTS.md`, что генерация идёт сначала.

### Вариант Y. Коммитить и проверять дрейф в CI

Артефакты в git. В `ci.yml` после `npm ci` шаг `npm run gen`, затем `git diff --exit-code -- api/generated` (команда стандартная; детерминированность вывода проверена, см. раздел 2).

- Плюс: итоговый OpenAPI виден в ревью; клонированный репозиторий сразу собирается и открывается в IDE.
- Минус: генерируемые файлы надо привести к виду, проходящему `prettier --check .` (иначе исключить через `.prettierignore`) и `oxlint`, а `.prettierignore` менять придётся один раз.
- Минус: любое изменение `.tsp` даёт два файла в диффе; забытая перегенерация ломает CI (то есть работает как предохранитель, но требует дисциплины).
- Минус: нужна правка `.github/workflows/ci.yml` (разрешено; запрещён только `hexlet-check.yml`).

### Вариант Z. Коммитить только `openapi.yaml`, `.d.ts` генерировать

Компромисс: файл OpenAPI в ревью виден, типы не шумят. Дрейф проверяется так же, как в Y, только для одного файла. Минус: две политики на два артефакта.

### Что точно пересечётся с существующим CI

- `typecheck` в корне вызывает скрипт во всех workspaces без `--if-present`: у `api/` он должен быть. Подходящее содержимое: `tsp compile . --no-emit` (флаг `--no-emit` есть в `tsp compile --help`) или `tsp compile . --warn-as-error`.
- `build` в корне запускает `build` во всех workspaces: в `api/` это `tsp compile .`.
- Кэш `actions/setup-node` с `cache: npm` продолжает работать, пока lockfile в корне.

## Рекомендация

1. Workspace `api/` с `main.tsp` и `tspconfig.yaml`; `@typespec/compiler`, `@typespec/http`, `@typespec/openapi3` с `^1.17.0` и обновлением одним пакетом; эмит в `openapi.yaml`, версия OpenAPI `3.1.0`.
2. Бекенд: собственный небольшой загрузчик, регистрирующий схемы из `openapi.yaml` (с заменой префикса `$ref`) и подключающий их к `schema.body`/`schema.response` по `operationId`; типы тел из `openapi-typescript`.
3. Фронтенд: `openapi-typescript` + `openapi-fetch`. Перед выбором решить конфликт `peerDependencies.typescript ^5.x` у `openapi-typescript@7.13.0` и `typescript ~7.0.2` в репозитории (проверено: `ERESOLVE`).
4. Сгенерированные OpenAPI и `.d.ts` не коммитить (вариант X): генерация корневым скриптом `gen`, подключённым перед `typecheck`, `test`, `build`, `dev`; тогда дрейфа нет и шаг в CI не нужен. Если команда предпочитает видеть OpenAPI в ревью, запасной вариант Y или Z: коммит плюс шаг `npm run gen && git diff --exit-code` в `ci.yml` и исключение артефактов из `prettier`.
5. Открытые вопросы для реализации (#11): способ обхода peer-конфликта; нужен ли `fastify-openapi-glue` (не проверялся) вместо своего загрузчика; как пробросить генерацию в `npm test -w backend`.
